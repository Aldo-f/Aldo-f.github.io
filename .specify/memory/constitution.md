# Aldo Fieuw Documentation Hub Constitution

## Core Principles

### I. Build Purity (NON-NEGOTIABLE)

The site MUST build cleanly with `mkdocs build --strict`: zero warnings, zero
errors, non-zero exit code is a failed build. Any feature that cannot pass a
strict build does not merge. Warnings are treated as errors because warnings
rot into breakage silently.

### II. Nav-Explicitness

Every content surface (page, section, blog, imported repo docs) MUST be
reachable through the explicit `nav:` in `mkdocs.yml`. Content not listed in
nav is orphaned and therefore forbidden to ship. Adding a content source
without its nav entry is an incomplete change.

### III. Upstream-First Feature Delivery

New features MUST be delivered through the platform's own supported extension
points (bundled Material plugins/extensions) before introducing new
dependencies. A feature that the installed toolchain already ships MUST NOT be
re-implemented with custom code or extra packages. New external dependencies
require explicit justification in the plan artifact.

### IV. Generated-Output Hygiene

Build output (`site/`), virtual environments (`venv/`), plugin import caches,
and other generated artifacts MUST NOT be committed. Anything regenerated by
`mkdocs build` is disposable by definition.

### V. Verified Before Deployed

A change is done only with real end-to-end evidence: strict build exit code +
served-output checks against the actual built site (HTTP status + body of key
routes from a running server). Claims of success without captured command
output are invalid. Deployment happens exclusively via CI on push to `main`;
no manual artifact pushes.

## Content & Deployment Constraints

- Site deploys to GitHub Pages via `.github/workflows/deploy.yml` on push to
  `main`; the workflow trigger branch must always match the working branch.
- `requirements.txt` is the single dependency declaration; local venv and CI
  must both install from it.
- Multirepo imports are pinned to remote branches/tags in `mkdocs.yml`; never
  reference floating local state.
- User-facing navigation labels follow existing style (title case, short).

## Development Workflow

1. Spec → Plan → Tasks artifacts exist under `specs/<NNN-feature>/` before any
   implementation code or configuration changes.
2. Tests/checks are written first and observed failing (RED), then the change
   is made and observed passing (GREEN).
3. Verification ladder: `mkdocs build --strict` → served-site route checks →
   push → confirm GitHub Actions run is green.
4. One logical change per commit/PR; unrelated cleanup stays out.

## Governance

This constitution supersedes ad-hoc practice for this repository. Amendments
require an updated version line (semver: MAJOR for principle
removal/redefinition, MINOR for new principles, PATCH for clarifications) and a
Sync Impact Report comment prepended to this file. All changes must demonstrate
compliance with Principle I and V before merge.
